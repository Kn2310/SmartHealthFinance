# 05.9 Observability & Operations

## Objetivo

Detectar, diagnosticar e resolver problemas técnicos e de negócio, preservando integridade financeira.

## Stack

OpenTelemetry:
- logs
- metrics
- traces

Logs estruturados em JSON.

## Níveis

TRACE / DEBUG / INFO / WARN / ERROR / FATAL.

## Contexto

- correlationId
- traceId
- spanId

Nunca registrar secrets ou dados financeiros desnecessários.

## Métricas

API:
- p50
- p95
- p99
- availability
- 4xx/5xx

Infra:
- PostgreSQL
- Redis
- RabbitMQ
- Outbox
- workers

Domínio:
- imports
- Open Finance
- health freshness
- forecast freshness
- insight generation
- AI

## SLOs iniciais

- API availability ≥99.5%
- API p95 ≤500ms
- API 5xx <1%
- Import ≥99% dentro do target
- Async ≥99% dentro do target
- Copilot success ≥98%
- Health freshness ≤5 min
- Forecast freshness ≤15 min

## Error budget

SLOs devem gerar ação operacional, não apenas dashboards.

## Alertas

P1/P2/P3/P4.

Alertas precisam ser acionáveis.

## Health

Liveness/readiness.
Graceful degradation.

## Data freshness

Monitorar atraso dos read models.

## Incidentes

Lifecycle:
detect → triage → mitigate → resolve → postmortem.

Runbooks devem existir para falhas relevantes.

## Retenção

Diferenciar logs, metrics, traces, audit e dados financeiros. Períodos exatos devem ser definidos antes do lançamento real.

## Princípio

> Não basta saber que o sistema falhou; precisamos identificar onde, por quê, qual impacto foi causado e se os dados financeiros continuam íntegros.
